# QoR (Quality of Results) 报告

以下是一份`iSTA`生成的QoR报告:

```
Path Group                  WNS        TNS     NVP      FREQ      WNS(H)     TNS(H)  NVP(H)
-------------------------------------------------------------------------------------------
clk                       9.300        0.0       0    1429MHz     -0.097       -7.6     100
-------------------------------------------------------------------------------------------
Summary                   9.300        0.0       0    1429MHz     -0.097       -7.6     100
-------------------------------------------------------------------------------------------
    CAP  FANOUT    TRAN    TDRC      CELLA    BUFS     LEAFS       TNETS      CTBUF    REGS
-------------------------------------------------------------------------------------------
      0       0       0       0       2219      ~K        1K          ~K          ~       ~
-------------------------------------------------------------------------------------------

NVP    - No. of Violating Paths
FREQ   - Estimated Frequency, not accurate in some cases, multi/half-cycle, etc
WNS(H) - Hold WNS
TNS(H) - Hold TNS
NVP(H) - Hold NVP
```

报告主要可以分为两个部分:

- 以`Path Group, WNS, TNS ...`为表头的**时序结果摘要表** : 他主要用于芯片在时序上是否达标.
- 以`CAP, FANOUT, TRAN ...`为表头的**设计规则与实例统计表** : 他主要统计了芯片中有多少单元违背了基本电气规则, 使用了多少硬件资源.

## 时序结果摘要表

时序结果摘要表中自左向右分别是:

- `Path Group`: 表示了这一行汇报的是在哪个 **Path Group** 分析出的时序结果
- `WNS`: 全称 **Worst Negative Slack**, 表示本 **Path Group** 中时序情况最差的那条路径的 **时序裕量**. 值为正时, 说明存在裕量;
  而值为负时, 说明存在时序违例.
- `TNS`: 全称 **Total Negative Slack**, 表示本 **Path Group** 中所有发生了时序违例的路径的 **裕量** 之和.
  如果所有路径均满足时序约束, 值为零.
- `NVP`: 全称 **Number of Violating Paths**, 表示本 **Path Group** 中发生了时序违例的数量. 
  如果所有路径均满足时序约束, 值为零.
- `FREQ`: 预估频率. 通过时序结果推算出的芯片理论最高频率.
- `WNS(H)`: **Hold WNS**, 含义和 `WNS` 相同, 但是是对时序路径做 **保持时间检查(Hold Time Checking)** 的结果
- `TNS(H)`: **Hold TNS**, 含义和 `TNS` 相同, 但是是对时序路径做保持时间检查的结果
- `NVP(H)`: **Hold NVP**, 含义和 `NVP` 相同, 但是是对时序路径做保持时间检查的结果

在这张表中, 我们主要需要检查的内容有两个:
- 有时序违例吗: 也就是 `NVP`, `NVP(H)` 是不是都是零了
  - 时序违例时, 违例的严不严重: `WNS`, `WNS(H)`; 容易修复吗: `TNS`, `TNS(H)`
- 时序不违例时, 理想情况下芯片到底能跑多快: `FREQ`
  - 当然, 需要注意的是, 特别是在比较早期的 `STA` 过程, 比如还没有进行布局布线时, `FREQ` 会偏高.
    通常来说, 芯片是没法顶着 `FREQ` 说明的频率跑的

## 设计规则与实例统计表

设计规则与实例统计表内部也可以分为两组: **基本电气信息检查** 以及 **硬件资源汇总**

`CAP`, `FANOUT`, `TRAN`, `TDRC`属于 **基本电气信息检查** :
- `CAP`: 指示了发生 **最大电容违例(Capacitance Violations)** 的单元数量. 当发生最大电容违例时, 说明这个单元已经无法驱动他需要输出的引脚了.
  可以使用驱动能力更强的单元或者增加`BUF`单元解决.
- `FANOUT`: 指示了发生 **最大扇出违例(Fanout Violations)** 的引脚的数量. 通常我们会人为规定一个引脚的最大扇出数.
  比如说64, 那么当一个输出引脚同时驱动了100个输入引脚时, 就会发生最大扇出违例. 同样的, 我们可以通过手动插入缓冲树解决.
- `TRAN`: 指示了发生 **最大转换时间违例(Transition Violations)** 的时序弧的数量. 一个巨大的转换时间, 不仅仅会拖慢芯片的时序情况,
  还会加剧电路的短路功耗. 而导致转换时间过大的原因, 通常是扇出过多, 或负载容抗过大.
- `TDRC`: 全称 **时序设计规则检查总违例(Timing Design Rule Checks)**, 通常是`CAP`, `FANOUT`, `TRAN`之和.

当**基本电气信息检查** 发生违例时, 芯片也是无法正常工作的. 
但是通常而言, 我们不需要手动修复这些违例, 在后端设计中, 会有专门的EDA工具负责搞定他们.

`CELLA`, `BUFS`, `LEAFS`, `TNETS`, `CTBUF`, `REGS`属于 **硬件资源汇总**:
- `CELLA`: 总标准单元面积, 他能直观体现芯片的面积, 通常而言, 布局布线后的芯片面积会比这个数值更大.
- `BUFS`: 统计设计中非时序的驱动单元数量, 他们通常用于修复**保持时间违例**, 优化**转换时间**以及构建**时钟树**
- `LEAFS`: 叶子单元的数量, 通常指最底层实例化的标准单元总数
- `TNETS`: 总信号线网数量
- `CTBUF`: 时钟树缓冲器的数量
- `REGS`: 寄存器数量

当芯片没有时序违例以及电气违例时, 我们才需要关注这里的信息.
